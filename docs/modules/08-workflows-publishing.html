Automated workflows and publishing

Turn the steps you now repeat into a skill with built-in stop points, add a reviewer and a guaranteed check, and put the site on the internet with GitHub Pages.

By the end of this module you can

  • Decide, for any task, whether it belongs in chat, on a canvas, with the agent, or in an automated workflow.
  • Build a /new-page skill that applies your system, runs review, and stops for your approval.
  • Add a hook that guarantees a check, and publish a site with GitHub Pages.

Anthropic's own advice on agents applies here: use the simplest workflow that works before reaching for autonomy. Automate a workflow only after you have run it by hand several times and know where it goes wrong — those are where the stop points go.

Three mechanisms

  • A skill (.claude/skills/new-page/SKILL.md) is a written procedure Claude follows when you type /new-page. It can call on your context files, run other steps, and — crucially — be told to stop and wait for you.
  • A subagent (.claude/agents/ux-reviewer.md) is a specialist with its own instructions and limited tools. A read-only reviewer that checks Nielsen's heuristics, WCAG AA and the brand voice cannot break anything, and gives you a second opinion before you look.
  • A hook is a small script that runs automatically at a set moment, such as after every file edit. Instructions in CLAUDE.md are advisory; Claude can forget them. A hook is deterministic; it always runs. Use hooks for the checks you refuse to skip.
Prompt: the reviewer

Create a read-only subagent called ux-reviewer in .claude/agents/ with only Read, Grep and Glob tools. It reviews the files I name against Nielsen's ten usability heuristics, WCAG 2.2 AA (contrast, semantic HTML, alt text, keyboard focus order) and the brand-voice skill. It reports issues grouped by severity — blocker, major, minor — each with file and line, the criterion violated, and a proposed fix. It never edits.

Prompt: the guaranteed check

Add a hook that runs an HTML validation and accessibility check on any file in docs/ after every edit, and shows me the result. Explain where the hook lives, what event triggers it, and how I would turn it off. Use a tool that needs no sign-up.

The hook will land in .claude/settings.json and look roughly like this — the exact shape is in the Claude Code docs, which is why the prompt asks Claude to explain what it wrote:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "npx html-validate docs/**/*.html" }
        ]
      }
    ]
  }
}
Prompt: the workflow skill

Create a skill called new-page. When I run /new-page with a brief, it: reads the brief; applies DESIGN.md, CLAUDE.md and the brand-voice skill; builds the page; starts the preview and takes screenshots at 390px and 1440px; runs the ux-reviewer subagent; shows me the screenshots and the review; then STOPS and waits for my approval before committing. Write the skill so each step is visible to me as it happens.

Publishing with GitHub Pages

GitHub Pages serves a folder of your repository as a website, free. This site is published from its docs folder. The steps, once the repository is on GitHub:

  1. On github.com open the repository, then Settings → Pages.
  2. Under "Build and deployment" choose "Deploy from a branch", pick main and the /docs folder, and save.
  3. Wait a minute or two. The page shows the public address when it is live.
  4. Every push to main republishes automatically.

Two details that save an hour of confusion: an empty file called .nojekyll in the docs folder stops GitHub from trying to process your files; and the site's address is https://your-name.github.io/repository-name/, so links inside the site must be relative (assets/style.css, not /assets/style.css).

Prompt: publish

This site lives in docs/. Make sure docs/.nojekyll exists and every internal link is relative. Commit and push. Then walk me through enabling GitHub Pages from the main branch and the docs folder, one step at a time, and give me the address when it is live.

Writing a workflow down

Every skill you create is also documentation. Keep each one to the same shape so a colleague can read it: purpose · inputs (which context files) · steps · the human checkpoint · definition of done · a sample output. CLAUDE.md, the skills and the subagents live in the repository and compound: every correction makes the next run better.

Exercise: ship this tutorial

  1. In the studio-site project, create the ux-reviewer subagent and the hook. Edit a page badly on purpose — remove an image's alt text — and watch the hook catch it.
  2. Create the /new-page skill. Run it with a three-line brief for a "Services" page. Do not approve the first result; redirect once, then approve and let it commit.
  3. Publish the site with GitHub Pages. Open it on your phone.
  4. Write the workflow down in the six-part shape and save it as docs/runbooks/new-page.md.

Checkpoint

  • A hook ran without you asking, and you saw its output.
  • /new-page builds, reviews, shows evidence and stops before committing.
  • A public URL shows your site, and you have opened it on a phone.
